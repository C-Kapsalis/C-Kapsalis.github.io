I Built an AI Marketing Analyst. Then I Tested Whether It Actually Helped

An experiment with synthetic marketing data, analytical traps and two configurations of Claude Haiku.

I built Devil's Analyst because getting an AI model to produce an answer is relatively easy. Getting it to challenge the assumptions behind that answer, distinguish evidence from explanation and recommend an action that can withstand scrutiny is harder.


Devil's Analyst is an open-source collection of analytical skills for AI agents. It covers marketing metrics, attribution, experiments, research, pricing, channel performance, Power BI models and reporting.


I had written the skills, assembled benchmark cases and created graders to evaluate their outputs. The question was whether giving an AI agent a structured body of analytical knowledge improves the work it produces.


I compared outputs with and without the relevant skills, using identical prompts and synthetic data. The results were mixed. One broad evaluation showed almost no difference. A smaller follow-up found better performance on some reporting and audit tasks, but also exposed failures that required changes to the skills.


Neither result establishes a general performance improvement. The experiment is useful because it shows where the approach helped, where it did not, and what I still need to test.


The problem: an answer is not an analysis

Consider an ordinary marketing report. A dashboard shows that conversion rate has declined. Someone identifies a recent landing-page redesign as the likely explanation. A recommendation follows: revert the redesign.


There are three separate jobs: establish whether the decline is real, investigate what might explain it, and decide what action the evidence justifies.


A correctly calculated metric does not establish its interpretation. A plausible explanation does not establish causality. An action based on an untested explanation remains untested.


I wanted Devil's Analyst to make the reasoning explicit: define the metric, validate the comparison, investigate competing explanations, examine the evidence and connect recommendations to something measurable.


Figure 1. Analytical sequence from observation through validation, competing hypotheses, evidence and action. Invalid comparisons should return to data validation rather than proceed to diagnosis.


What I built

Devil's Analyst is an open-source collection of 16 agent skills and a session hook. The project contains 229 numbered analytical checks, alongside formulas, diagnostic playbooks, adversarial questions and review procedures.


Its workflows cover metric definitions, movement decomposition, experimental design, evidence checks, diagnosis, recommendations and review of existing reports. The review workflows also examine whether correct work should remain unchanged.


The intention is to make analytical reasoning easier to inspect and challenge. The skills should not make an agent produce longer reports or more warnings by default.

Both arms received the same task and identical input data for each case. I used synthetic marketing data because I needed to know what the correct answer should be. Each benchmark case contains deliberately constructed analytical problems, supporting exports and, where appropriate, decoys that should not be flagged.


The repository contains 110 cases: 62 focused analytical traps, 36 draft reports with supporting exports, and 12 audits and reviews. Of these, 105 are generated by scripts that calculate expected answers; five early cases are hand-written.

The first evaluation: breadth

On 17 October 2026, I ran all 36 draft-report cases. Each case received three runs per arm, producing 216 runs in total.


The model was Claude Haiku 5.5 in Claude Code. The evaluation used the default Claude plugin-evaluation judge, with three votes per grader and majority agreement determining the result.

Case 2: knowing when not to recommend changes

I included a clean-control case: an existing report without the planted problems the review skill was designed to identify.


An analytical reviewer that always finds something wrong creates unnecessary work and can undermine confidence in correct work.


Arm A concluded that the report was ready to send and passed all three graders. Arm B proposed three changes and passed one grader.

Case 3: a failure in SEO diagnosis

Both arms failed to distinguish declining market demand from a problem with the website's SEO performance.


The skill-assisted arm did not solve the case. I traced the failure to a missing diagnostic step. The instructions required the agent to rule out measurement problems before investigating behaviour, but did not explicitly ask whether the whole market had moved.


I added a general rule: before diagnosing a decline as an organisation-specific problem, investigate whether the category or competitors experienced the same movement.


The case was rerun with the revised skill, and the previously failing graders passed. This is useful engineering feedback, but not independent validation. I changed the instructions after seeing the failure, and the revised case was familiar to me.

What the experiment does not prove

The data is synthetic. The planted problems make correct answers easier to establish, but real marketing data is messier and often contains questions that cannot be resolved from an export alone.


The first evaluation did not demonstrate a meaningful overall improvement. The 0.94 versus 0.93 mean score difference is too small to support that conclusion.


The second evaluation was small: 17 cases and one run per arm. A single changed result can materially affect the comparison.


I was also the judge. I wrote the cases, skills and graders, and knew which arm produced each answer. Another reviewer could disagree with some assessments.


The experiment did not test the complete plugin-routing mechanism. Skill-assisted agents were directed to read relevant files. This did not test whether the session hook and routing mechanism would reliably select the right skill in an ordinary user session.


Neither arm could execute code in the second evaluation. The skills recommend using code for calculations where appropriate, so this experiment did not test that part of the intended workflow.


Finally, the results are specific to Claude Haiku in Claude Code. They do not establish that the same results will occur with other models, agents or platforms.


What I want to test next

The next evaluation should use more repetitions per case and arm to distinguish consistent behaviour from variation between runs.


I also want independent grading. Another reviewer should assess anonymised outputs without knowing which arm produced them.


The evaluation should separate whether the agent identified the problem, calculated correctly, avoided false alarms, distinguished observations from hypotheses, recommended an evidence-supported action and explained how to evaluate it.


I also want cases created by people other than me. Finally, I want to test the complete agent workflow, including routing, data access and code execution.


The work between an answer and a decision

We are giving AI agents access to more data systems, reporting tools and analytical workflows. Access to data does not automatically produce sound analytical judgement.


An answer can rely on an unstable metric definition, an unfair comparison or an explanation the evidence does not support. I built Devil's Analyst to make those assumptions more visible and give an agent a structured way to challenge them.


The first benchmark did not show a meaningful overall improvement. The smaller follow-up produced encouraging results in some reporting and review tasks, while exposing failures that required changes to the skills.


I would rather publish an inconclusive result and explain what I learned than turn a small difference into a performance claim. The next step is to make the evaluation more independent, reproducible and difficult for my own assumptions to influence.
