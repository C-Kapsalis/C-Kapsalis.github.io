I Built a Power BI Toolkit for the Work Between Business Questions and Reliable Models

An open-source workflow for prototyping semantic models, catching TMDL defects, keeping client models aligned and standardizing reports.

A marketing team asks a familiar question: which campaigns bring in profitable customers? The answer sounds simple until someone has to turn it into a Power BI model.


What counts as a customer? Which date defines acquisition? Is revenue recognised at order date or payment date? How should refunds be handled? Does the business already have a customer dimension, or does the data need to be joined from several systems?


The people who understand the business question are often not the people who build the semantic model. The request moves through a backlog, assumptions are made, and the first draft comes back shaped by what the engineer could infer.


Power BI's Project format (PBIP) and Tabular Model Definition Language (TMDL) make semantic models easier to version, inspect and review as text. But text-based source control does not, by itself, make model changes safe. A missing table reference, duplicated lineage tag, malformed field parameter or renamed measure can still break a report.


I built swift-pbi to address the work around those models: translate business questions into an engineering hand-off, validate and repair mechanical defects, keep template-based client models aligned without erasing legitimate differences, and standardise recurring report layouts.


It is not a replacement for Power BI Desktop, Tabular Editor or deployment tooling. It is a set of open-source skills and command-line tools that make parts of the development workflow more inspectable and reproducible.

The gap is not just between data and dashboards

A semantic model is an executable interpretation of a business. Tables, relationships, measures, calculation logic, formats and descriptions encode decisions about how the organisation understands its activity.


A request such as “show customer retention by acquisition cohort” hides several design questions:


- What is the grain of the customer and transaction tables?

- Which event marks acquisition?

- What constitutes an active or retained customer?

- How are cancellations, refunds and reactivations represented?

- Which dimensions should filter the measure?

- What source systems and refresh rules are authoritative?


If these questions remain implicit, the engineer has to guess or return for clarification. Either way, the first model can become a negotiation over assumptions rather than a useful starting point.


The prototype-model workflow in swift-pbi treats the business request as a specification problem. It interviews the requester, records assumptions and open questions, creates a star-schema proposal, builds a PBIP project with fictional sample rows, validates the result and produces a hand-off package.


The package is not intended to pretend that unknown source-system details have been solved. It separates what can be modeled from what the engineering team still needs to decide: source of truth, refresh strategy, historical retention, row-level security and production credentials.

Start with a specification, not a guessed dashboard

The prototype workflow asks for the business questions, relevant entities, measures, relationships and constraints before generating the model.


For example, a fictional bike repair workshop might need to understand service revenue, repeat customers, technician utilization and parts performance. Those questions imply different grains and relationships:


- A work order is not the same thing as a work-order line.

- A customer-level count should not be calculated from a dimension if the intended population is defined by a fact table.

- A ratio needs a clearly defined numerator and denominator at a compatible grain.

- A date table needs an explicit relationship to the event date being analysed.


The first draft of a bike-shop specification in the repository's reproducible demo failed its hand-off checks. It contained three P1 findings: an orphan customer key, a per-customer ratio counted from the dimension rather than the fact table, and a measure without a description.


After correcting the specification, the hand-off profile reported zero P0, zero P1 and zero P2 findings. The model build contained six tables, 29 columns, six measures and four relationships. The generated PBIP report had one empty page; this was a model prototype and hand-off package, not a finished business dashboard.


Rebuilding the corrected specification produced byte-identical files. That matters because a reproducible build makes it possible to review the specification and the generated artifacts separately.


These are repository demo results on fictional data, not a claim that the workflow can infer every organization's business definitions.

Treat TMDL validation as a preflight check

PBIP and TMDL make model metadata reviewable in Git. They also expose the model to ordinary text-file defects and consistency problems.


The swift-pbi preflight workflow uses tmdl-preflight, a separate open-source command-line tool pinned to version 1.2.1 in the current project configuration. The tool reports 119 rules covering TMDL structure and conventions. Twenty-five rules have mechanical fixers, although four of those fixers run only when explicitly selected because they are unsafe to apply indiscriminately.


The repository includes a deliberately broken fictional bike-shop model. Running the preflight check reports 12 findings:

The distinction between a validator finding and a Power BI Desktop failure is important. In a separate Windows test bench using the earlier v1.1.0 tools, I tested each planted defect individually in Desktop. The duplicate lineage tag prevented the project from opening. The field-parameter comma did not prevent the model from opening, but visuals using that parameter failed. The missing table reference and placeholder lineage tag did not stop Desktop from opening the model.


The current macOS demo uses v1.2.1 and records the tool output, not a new Desktop compatibility test. The Windows bench has not been rerun against v1.2.1. I keep those claims separate rather than treating every lint error as a load blocker.


After the fixer runs, it reports four mechanical repairs: add the missing table reference, replace the duplicate lineage tag, replace the placeholder tag and remove the orphan comma. An independent re-check reports zero errors and zero warnings. Eight informational findings remain because they need a human decision, such as writing meaningful descriptions or deciding which calendar columns are required.


A second fix run changes nothing.

Fix what is mechanical; leave meaning to people

A linter can detect that a description is missing. It cannot reliably invent the business meaning of a measure.


A fixer can replace a duplicated identifier. It should not decide whether a measure's definition is semantically correct. A style rule can identify a missing format string, but the appropriate format depends on what the measure represents.


The preflight skill therefore follows a constrained sequence:


1. Run the check and capture its output.

2. Explain each finding and its likely impact.

3. Show the proposed changes or dry run.

4. Ask for consent before editing.

5. Apply only supported mechanical fixes.

6. Run the check again and report what remains.


The agent is instructed to quote counts from tool output rather than estimate them. It must not claim that a model opens in Power BI Desktop merely because the validator passes.


This is a deliberately narrow role for an agent. The command-line tool determines what it found. The agent explains the result and mediates the workflow. The human remains responsible for approving file changes and deciding questions of business meaning.


Figure 4. Consent-based repair loop: inspect, explain, show diff, obtain approval, fix, re-check. Human judgement remains in the loop for semantic and documentation decisions.


Keep client models aligned without making them identical

The fleet-drift workflow addresses a different problem: organizations and agencies that maintain several Power BI models derived from a shared template.


A template may define common revenue measures, dimensions and relationships. Each client model may also have legitimate differences: additional measures, different source connections, a deliberately absent table, or a client-specific calculation.


A naïve synchronization process can erase those differences. A useful fleet process must distinguish accidental drift from intentional variation.


swift-pbi uses tmdl-drift-doctor to compare a template with spinout models, classify differences, apply an explicit allowlist and maintain a ledger of retired objects. A fleet.yml configuration records approved exceptions.

The repository demo plants drift across four fictional spinout models: changed DAX, a lost currency format, a deleted measure, a dropped column, a relationship changed to bidirectional filtering, a measure moved to another table, and a spinout-only measure.


Before remediation, detection reports eight actionable findings and one advisory. The remediation command applies six fixes under an explicit allowlist. Afterwards, detection reports zero actionable findings, and preflight reports zero errors in all four spinouts.


The demo then retires a measure from the template. The process refuses to proceed against a stale baseline. After the baseline is recaptured, ordinary remediation skips deletions. One spinout is explicitly marked as retaining the measure. A second explicit confirmation is required to remove it from the other three.


That second gate is intentional. Deleting a measure from a client model is not equivalent to correcting a formatting inconsistency. The workflow makes destructive synchronization a separate decision.

Standardize reports through a model-driven canvas

A consistent semantic model does not guarantee consistent reports. Teams often rebuild similar chart layouts repeatedly, and small differences in field bindings, bookmarks and formatting accumulate.


The chart-style skill uses pbi-plot-styler to maintain a standardized combo-chart canvas. The example uses field parameters for plot axis, legend and measures, with bookmarks representing recurring analytical questions. Styling is driven from the model rather than manually copied across every report.


In the recorded coffee-roastery example, the check command found zero errors. The style command rebuilt one of one combo charts, using five line measures and excluding one measure assigned to the columns role. A second run rebuilt zero charts.


I then renamed a measure in the model without updating the report. The check reported two binding errors, BND001 and BND002, identifying the visual that still referenced the old measure name.


This is a useful boundary for automation. The tool can detect a broken binding and rebuild a known layout. It cannot decide whether the chart is the right way to answer a business question.

The architecture: skills coordinate, tools do the work

swift-pbi is not one monolithic application. It combines agent instructions with four focused command-line tools:

The tools are invoked through uvx against pinned releases. This avoids relying on a globally installed version that may differ between machines.


The skills are designed to work with terminal-capable agents such as Claude Code, Codex, Cursor, GitHub Copilot, Cline and Kiro, or any agent that reads AGENTS.md. In chat-only environments, an assistant can help interview the requester, write a specification and explain pasted output, but it cannot execute the local tools.


That distinction is part of the design, not a footnote. A workflow should say clearly which steps were executed and which were only described.

What the tests do not prove

The examples are reproducible, but they are not production validation across every Power BI model or organisation.


The models and client spinouts in the demo are fictional. The generated sample data is not customer data. Passing preflight establishes that the tested rules found no remaining errors or warnings; it does not establish that every measure expresses the intended business definition.


The current macOS demo output does not prove that every generated project opens in Power BI Desktop. The separate Windows bench was performed with v1.1.0, and has not been rerun with the v1.2.1 tool pin.


The agent evaluation is also separate from the tool demo. In runs on 21 October 2026 against the v1.1.0 tools, the plugin arm scored 0.90 compared with 0.84 without the plugin across 37 case-runs. The per-suite mean delta was positive in four of five runs, with a median difference of +0.05. This is an early, narrow evaluation, not evidence that the skills improve every Power BI task or generalize to larger models. The project includes a complexity ladder intended to test progressively larger models.


The project does not deploy models to Fabric workspaces. It does not replace Tabular Editor's broader best-practice analysis, ALM Toolkit's model comparison and deployment workflows, Fab Inspector's report and Fabric-item checks, or Microsoft's Fabric deployment tools. Those tools address different parts of the lifecycle and can be used alongside swift-pbi.


Why I built it this way

The central design decision is to keep the boundaries visible.


A business request should become a specification before it becomes a model. A validator should report what it can establish, not what a human hopes it means. A fixer should repair mechanical defects without inventing semantics. A template synchronization tool should preserve documented client differences and require explicit confirmation for destructive changes. An agent should explain tool output rather than manufacture it.


These constraints make the workflow less magical and more useful. They also make failures easier to investigate. When a report is wrong, the team can ask whether the problem began in the business definition, the model specification, the TMDL, the report binding or the interpretation of the output.


The next step is broader testing against larger and less controlled models, including counterexamples from practitioners. The project is open source because those counterexamples are more valuable than a polished demo that only confirms the assumptions I started with.


If you work with PBIP, TMDL or template-based Power BI delivery, I would be interested in cases where the tools report a defect they should ignore, or miss one they should catch.
